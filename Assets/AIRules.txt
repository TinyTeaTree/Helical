# Helical Project - AI Rules & Conventions

## Core Architecture (Core Foundation)

### Overview
This project follows the "Core Foundation" architecture that splits the game into:
- **Features**: Game logic and functionality (MVC pattern with Record + Interface + Implementation)
- **Services**: Agnostic utilities and cross-cutting concerns
- **Agents**: Cross-cutting lifecycle management and coordination
- **Resolvers**: Partial interfaces exposing specific functionality from Features/Services

### Assembly Structure
```
Scripts/
├── Game.asmdef (references: Agents, Core, Plugins)
├── Agents/ (Agents.asmdef - references: Core)
├── Core/ (Core.asmdef)
├── Features/ (organizational folder)
├── Services/ (Services.asmdef - references: Core, Plugins)
├── Factories/ (organizational folder)
└── System/ (GameBootstrap.cs)
```

### Interface Hierarchy
All injectable interfaces inherit from `IInjectableInterface`:
- `IFeature` : Core game functionality
- `IService` : Agnostic utilities
- `IAgent` : Lifecycle coordination
- `IResolver` : Partial API exposure

## Feature Pattern

### Structure
Each Feature consists of:
- **Feature Script** (e.g., `BattleUnitsFeature.cs`): Main logic, inherits from `BaseVisualFeature<VisualType>` or `BaseFeature`
- **Interface** (e.g., `IBattleUnits.cs`): Public API, inherits from `IFeature`
- **Record** (e.g., `BattleUnitsRecord.cs`): Data storage, inherits from `BaseRecord`
- **Visual Script** (optional): MonoBehaviour control, inherits from `BaseVisual`
- **Config** (optional): Readonly data from ScriptableObjects

### Feature Creation Pattern
```csharp
public class ExampleFeature : BaseVisualFeature<ExampleVisual>, IExampleFeature
{
    [Inject] public ExampleRecord Record { get; set; }
    [Inject] public IOtherService Service { get; set; }

    // Implementation of IExampleFeature methods
}
```

### Interface Pattern
Feature Interfaces are designed for **cross-feature communication only**.

```csharp
public interface IExampleFeature : IFeature
{
    // Only methods that other Features need to call
    void DoSomethingOtherFeaturesNeed();
    UniTask GetDataForOtherFeatures();
}
```

### Interface vs Feature Public API
- **Interface**: Cross-feature communication API
- **Feature Public Methods**: Internal logic accessible by Visuals via `this.Feature`

**Rule**: Don't expose Visual-specific interactions in Interfaces just because Visuals use them.

**Example**: A button press on Visual should not be in Interface - other Features shouldn't press buttons. Use `this.Feature.HandleButtonPress()` directly instead.

Visuals access their Feature via the `Feature` base property:
```csharp
public class ExampleVisual : BaseVisual
{
    private void OnButtonPressed()
    {
        // Direct access to Feature's public API
        this.Feature.HandleButtonPress();
        // NOT: Some other feature calls this button press
    }
}
```

### Record Pattern
```csharp
public class ExampleRecord : BaseRecord
{
    public List<SomeData> Items { get; private set; } = new List<SomeData>();
    // Only serializable data - no Unity objects, tasks, callbacks, etc.
}
```

## Resolver Pattern

### Overview
Resolvers are partial interfaces that expose specific functionality from Features or Services without requiring injection of the entire interface. This improves dependency management by allowing granular control over what functionality is accessible.

### Resolver Interface
```csharp
public interface IExampleResolver : IResolver
{
    // Only expose the specific methods needed
    bool IsExampleCondition();
}
```

### Feature with Resolver
```csharp
public class ExampleFeature : BaseFeature, IExampleFeature, IExampleResolver
{
    // Implement both full interface and resolver
    public bool IsExampleCondition() { /* implementation */ }
}
```

### Resolver Registration
```csharp
protected override void AddFeatures()
{
    var exampleFeature = new ExampleFeature();
    _features.Add<IExampleFeature>(exampleFeature);
    _resolvers.Add<IExampleResolver>(exampleFeature); // Register resolver
}
```

### Resolver Injection
```csharp
public class ConsumerFeature : BaseFeature
{
    // Inject only the resolver, not the full feature
    [Inject] public IExampleResolver ExampleResolver { get; set; }
}
```

### Service Registration
Services are registered in `GameBootstrap.AddServices()`:
```csharp
_services.Add<IExampleService>(new ExampleService());
_services.Add<ISummoningService>(new SummoningService()); // Note: SummonerService = SummoningService
```

## Agent Pattern

### Agent Creation
```csharp
public class ExampleAgent : BaseAgent<IExampleAgent>, IExampleAgent
{
    public async UniTask SomeEvent()
    {
        // Coordinate across multiple features/services
        foreach (var feature in _features)
            await feature.SomeEvent();
    }
}
```

### Agent Registration
Agents are registered in `GameBootstrap.AddAgents()`:
```csharp
_agents.Add<IExampleAgent>(new ExampleAgent());
```

## Dependency Injection

### [Inject] Attribute
- Used for automatic dependency resolution
- Only works in Features and Services
- Properties must have both getter and setter
- Injected via interface types only

```csharp
[Inject] public IGrid Grid { get; set; }
[Inject] public BattleUnitsRecord Record { get; set; }
```

## Null Checking Rules

### ✅ DO add null checks for:
- Method return values that can be null
- Fields marked `[CanBeNull]`
- Nullable types (`Type?`)

### ❌ DON'T add null checks for:
- `[SerializeField]` components (assume they are assigned)
- Feature injections (`[Inject]` properties)
- Record properties
- Asset references loaded via SummoningService
- Resource loads

## Async Programming

### UniTask Usage
- Use `UniTask` instead of `Task` or `async () =>`
- Use `UniTask.CompletedTask` for void async methods
- Use `UniTask.WhenAll()` for parallel operations
- Use `UniTask.Delay()` for delays

### Common Patterns
```csharp
public async UniTask ExecuteAction()
{
    await UniTask.Delay(1000);
    // Do something
    return UniTask.CompletedTask;
}
```

## Data Management

### Records vs Configs vs AssetPacks
- **Records**: Mutable game state data, can be saved/loaded, single instance
- **Configs**: Readonly data from ScriptableObjects, multiple instances possible
- **AssetPacks**: Containers for resources/assets to load, loaded via SummonerService

### Record Persistence
Records that should persist are registered in `BootstrapSavedRecords()`:
```csharp
saveService.AddSaveRecord(_records[typeof(PlayerAccountRecord)]);
```

### AssetPack Pattern
```csharp
public class ExampleAssetPack : BaseAssetPack
{
    public GameObject Prefab1;
    public Material Material1;
    // Asset references loaded by SummonerService
}
```

### AssetPack Loading
```csharp
_assetPack = await Summoner.SummoningService.LoadAssetPack<ExampleAssetPack>();
```

### SummonerService (Instantiation Service)
The SummonerService handles:
- **Resource Loading**: `LoadResource<T>(string path)` for Resources folder
- **AssetPack Loading**: `LoadAssetPack<TAssetPack>()` for complex asset collections
- **Asset Instantiation**: `CreateAsset<T>(T loadedAsset, Transform parent)`
- **Provider Registration**: `SetProvider(Type type, BaseAssetPackProvider provider)`

AssetPacks use providers registered in `GameBootstrap.BootstrapSummoningService()`:
```csharp
summoner.SetProvider(typeof(ExampleAssetPack), new ResourceAssetPackProvider("Path/To/AssetPack"));
```

## Unity Conventions

### Scene Structure
- **Empty Main Scene**: Only GameBootstrap GameObject
- **Managed Lifecycle**: All visuals created/destroyed through Features
- **No Merge Conflicts**: Features don't exist in scene hierarchy

### Asset Organization
- Use Resources folder for prefabs referenced by ResourceFactory
- AssetPacks loaded via SummonerService (SummoningService)
- Address system for resource paths

### ScriptableObject Rules
**HARD RULE**: ScriptableObjects (SOs) and Configs are **purely for data storage only**
- ❌ **NEVER** add functionality, logic, or methods to SOs/Configs (except simple getters)
- ❌ **NEVER** add constructors to SOs/Configs
- ✅ **ONLY** use serialized fields and simple getter properties
- ✅ Simple getter helpers are acceptable (e.g., `public int MaxValue => _maxValue;`)

**Rationale**: SOs are Unity's data containers. Keep them pure to avoid serialization issues, maintain editability in Inspector, and ensure they're just data structures.

## Naming Conventions

### Files and Classes

## Common Patterns

### Agent Coordination
```csharp
public UniTask AppLaunch()
{
    List<UniTask> tasks = new();
    foreach (var receiver in _features)
        tasks.Add(receiver.AppLaunch());
    return UniTask.WhenAll(tasks);
}
```

### Feature Communication
Features communicate through:
- Shared Records
- Agent coordination
- Direct interface calls (when appropriate)

### Visual Updates
```csharp
protected async UniTask CreateVisual()
{
    _visual = await _factory.Create<VisualType>();
    _visual.SetFeature(this);
}
```

- Interface-driven design
